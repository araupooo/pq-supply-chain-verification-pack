Post-Quantum Supply-Chain Verification Pack

Do four pinned post-quantum library targets rebuild deterministically from published source, and can a consumer trace each distributed binary or package back to that source with a verifiable hash or signature? All work done 2026-11-07 on one Linux x86_64 machine (gcc 13.3.0, cmake 3.28.3, Go 1.27.3, rustc/cargo 1.99.1).

Headline results

  • liboqs 0.16.0 — NONDETERMINISTIC with upstream defaults. Two clean Release builds differ: 1fdf54c7e56434c7c360593a81686de79f105a4ac213446710556298922e6114 vs fbd5dc65047d46d0d91c79da119a9665db6946e8fa7fc1f5a2c2a05ca4232d56 (both 38,720,354 bytes). Exactly 1 of 2,634 archive members differs (src/common/common.c.o): the only difference is the absolute build path embedded by GCC. -ffile-prefix-map removes it (objects identical 862b2aac3b28887a4ccd01f5ced7c429d649f014bf6f84e48b1f9663b5965c7e; re-archived libraries identical 9349b6d5d2301c3868ede55b58d5863c58f8a28c95f26febc38dd583de16849b).

How to re-run

python3 src/verify_hashes.py   # seconds: checks the 95 recorded hashes
./src/run_all.sh               # ~40-60 min: full rebuild of all targets

run_all.sh exits 0 only if every observed outcome matches its recorded expectation. Full methodology, matrix, limitations, and claim-to-evidence index: README.md, matrix.md, rubric.md, index.md, findings.md. Unedited logs and preserved artifacts: outputs/.

Limitations

  • liboqs: static library only; the -ffile-prefix-map fix was demonstrated at object + re-archive level, not by a third pair of full clean rebuilds; test suite not run; Makefiles used (Ninja not installed).
  • pq-crystals: ref/ only; KAT check is r1-vs-r2 self-consistency, not comparison against NIST-published KAT files.
  • Go: "rebuild" is defined explicitly in the rubric (stdlib ships in the toolchain); toolchain .asc UNVERIFIED.
  • Rust: determinism holds only under the stated conditions; ML-KEM-768 only; crate's own NIST KAT suite not run.
  • Single machine, single toolchain. Attestation/signature questions that hit GitHub API rate limits are labelled UNVERIFIED, not claimed either way.
